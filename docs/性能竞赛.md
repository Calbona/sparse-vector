# 性能竞赛

同一份数据、同一套计时口径，三个实现各跑一遍。

## 口径

- **数据**：同一条种子 LCG 生成的 100,000 个索引，落在 `[-1000000, 1000000]`。去重后三个实现都报告存下 97,558 个元素，先确认跑的是同一份数据。
- **计时**：预热 3 轮，正式 21 轮，取中位数，单位毫秒。
- **环境**：Windows 11 家庭中文版 10.0.26200，AMD Ryzen 9 7845HX；Node v24.14.0；MSVC 19.51.36231 `cl /O2`；rustc 1.98.1 `cargo --release`。

这是三种**实现**在各自原生运行时下的对比，不是语言之争。三个基准程序都在仓库根目录的 `benchmark/`，不进任何包。

## 结果

毫秒，中位数。

| 操作 | TypeScript | C++ | Rust |
| --- | --- | --- | --- |
| 散点写入 100,000 次 | 5.10 | 8.54 | 9.03 |
| 整表读取 100,000 次 | 2.01 | 1.21 | 6.99 |
| 由元素列表批量构造 | 6.23 | 8.48 | 9.07 |
| 迭代全部元素 | 18.47 | 8.40 | 0.70 |
| 替换默认值（全量剔除） | 3.92 | 2.15 | 2.50 |
| 替换相等判定（全量剔除） | 4.12 | 2.17 | 2.49 |
| 判等（相等的一对） | 5.41 | 0.30 | 0.45 |
| 求差（只差一个元素） | 5.34 | 0.22 | 2.72 |

## 怎么读

- **容器决定读出什么形状的数**。Node 的 `Map`、C++ 的 `unordered_map` 都是哈希表，Rust 的 `BTreeMap` 是 B 树；哈希表一次探测拿到值，B 树要跳几级。读取这一栏的排序正是这个形状：C++ 1.21、TS 2.01、Rust 6.99。C++ 从红黑树换成哈希表之后，读取从 11.93 落到 1.21，写入从 18.20 落到 8.54。这一栏比的是容器，不是语言。
- **迭代这一栏 C++ 和 TS 都含着一次排序**。三个基准程序都是"建一个向量再走一遍"，而哈希表和 Node 的 `Map` 都不保序，走之前得先把下标排回来；Rust 的 B 树本来就按序，这一笔不用付。C++ 那 8.40 里只有 0.06 是走，其余是重建顺序——单独量过：同一个向量建一次顺序、之后反复走，每遍 0.06 毫秒，比换容器前的 1.23 还快二十倍，因为顺着指针数组往前读能预取，而按序走红黑树每一步都要等上一个节点算出来。所以真实的取舍是：**写完立刻走一遍要付排序，此后怎么走都便宜**。
- **迭代慢不下来的另一个原因是分配**。Node 的迭代协议每借出一个元素就分配一个对象，九万多次迭代就是九万多个短命对象，所以它这一栏 18.47，比 C++ 和 Rust 都慢一个量级。
- **全量剔除**：三项接近。替换默认值或判定都是顺序扫一遍，容器之间的差距被摊平。
- **整向量比较**：C++ 最快——排序下标建一次就留在容器里，下一次比较直接归并两个紧凑的指针数组。TS 慢在取值路径：归并按序走一遍下标，每个下标都要回 `Map` 里 `has` 一次再 `get` 一次。
- Rust 自己的 `differences` 比 `is_equal_to` 慢约六倍，两边走的是同一次归并，多出来的是断言、克隆与 `Vec` 的构造。

## 复现

```sh
cd typescript && npm run build && cd ..
node benchmark/typescript/bench.mjs
```

```bat
cd benchmark\cpp
cl /nologo /std:c++17 /O2 /EHsc /utf-8 /I ..\..\c++\include bench.cpp /Fe:bench.exe && bench.exe
```

```sh
cargo run --release --manifest-path benchmark/rust/Cargo.toml
```

C++ 那条要先跑 `vcvars64.bat` 进 MSVC 环境。
